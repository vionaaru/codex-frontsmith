# Офис: локальная база и панель

Учёт одного автосервиса на этом компьютере: клиенты, автомобили, обращения, заказы работ, записи на время, задачи, каталог услуг и журнал действий. Бизнес-данные панель только показывает; в панели создаются и редактируются карточки клиентов, остальное меняется через Codex и узкие CLI-команды.

Контакты клиентов (имя, телефон, email, заметки, теги) хранит встроенный CRM — crmkit, через универсальный Customer Module (`office/customers/`). В офисной базе клиент — только `client_id` (`customers.id`), на который ссылаются бизнес-записи. Подробности — раздел 8.4 `docs/architecture/privacy-crm-integration.md`. Оплаты, склад, бухгалтерия, роли и синхронизация с Booking Flow не реализованы.

## Быстрый старт

```bash
npm install
npm run bootstrap        # один раз: CRM, Privacy runtime, профиль, база (схема последней версии), каталог услуг
npm run frontsmith       # панель http://127.0.0.1:4180 вместе с crmkit, Privacy Service и Codex App Server
npm run office:seed      # необязательно: учебный набор клиентов, заказов, задач и записей
```

Отдельные шаги для разработки: `npm run office:init` (миграции и проекция профиля), `npm run office:import` (каталог услуг и `demo-inquiry.json`), `npm run office:serve` (только панель, crmkit запускается автоматически). Все команды можно повторять: повторный запуск ничего не удаляет, не перезаписывает и не дублирует.

Новая база создаётся одной командой сразу до схемы последней версии, до появления первого клиента: таблица `customers` содержит только `client_id`, клиенты создаются через CustomerProvider. Прежняя модель с контактами в `customers` встречается только в старых установках; `npm run bootstrap` её определяет, но переносит контакты в CRM только явная команда `npm run crm:migrate-customers -- --dry-run`, затем `--confirm`.

## Где лежат данные

Единый приватный каталог — `.frontsmith/business/`. Здесь же находятся черновики, отчёты, настройки, вложения в `files/` и сформированный рабочий сайт в `website/`. Каталог целиком игнорируется Git. Изменения кода панели, CLI и SQL-миграций отправляются в Git независимо от данных.

Обновление сайта читает цены из БД и пишет `.frontsmith/business/website/`, не меняя отслеживаемый шаблон `website/`. Предпросмотр на порту 4173 показывает рабочий сайт; сборка демонстрации использует только публичный шаблон. SQLite и клиентские вложения не помещать в папку сайта.

| Что | Где | В Git |
| --- | --- | --- |
| База SQLite | `.frontsmith/business/office.sqlite` (+ `-wal`, `-shm`) | нет |
| Копии | `<data-root>/backups/office/` вне репозитория и рабочей области Codex; прежние — `.frontsmith/business/backups/` | нет |
| Профиль бизнеса | `.frontsmith/business/business.json` | нет |
| Схема | `office/db/migrations/*.sql` | да |
| Контакты клиентов (CRM) | `<data-root>/crm/` вне репозитория и рабочей области Codex | нет |

Путь к данным меняет `FRONTSMITH_BUSINESS_ROOT`: разрешён внешний каталог либо подкаталог `.frontsmith/`. Базу хранить на постоянном локальном диске, не в сетевой папке и не в serverless-окружении. Путь `.frontsmith/business/office.sqlite` сохранён для совместимости.

## Техническая основа

- SQLite через [better-sqlite3](https://github.com/WiseLibs/better-sqlite3) `12.9.0`, версия закреплена в `package.json` и `package-lock.json`. Это последняя версия с готовыми сборками для Node 20, 22 и 24 под Windows x64; ветка 13.x требует Node 22+. `node:sqlite` не используется: в Node 20 его нет
- Режим WAL, `foreign_keys = ON`, таблицы `STRICT`
- Слои: `lib/repositories.mjs` — SQL; `lib/operations.mjs` — прикладные операции и транзакции; `lib/work-reports.mjs` — атомарная регистрация ремонта поверх этих операций; `server.mjs` — HTTP GET API; `public/` — интерфейс; `scripts/office.mjs` — CLI
- Будущие кнопки панели должны вызывать те же прикладные функции, а не писать SQL
- При удалённом многопользовательском запуске нужна отдельная миграция на PostgreSQL; переключателя хранилищ нет

## Источники истины

- База — источник истины для клиентского учёта, задач, услуг и цен после первого импорта
- `business.json` остаётся источником профиля. Таблица `business` — его проекция; она обновляется командой `office:init`, редактировать её напрямую не нужно
- `npm run update:website` берёт прайс из каталога базы (`office/lib/catalog.mjs`). Если базы ещё нет, сайт работает в совместимом файловом режиме из `business.json`. Описания, фото и состав услуги для карточек сайта берутся из профиля по коду услуги
- После импорта цены в `business.json` больше не влияют на сайт. Повторный `office:import` покажет расхождения, но не перезапишет базу. Цена меняется только через `service:price`
- Markdown-черновики ответов и смет остаются файлами. Они не превращаются в заказы автоматически

## Схема и связи

```text
business (1 запись, проекция business.json)

customers 1─* vehicles
customers 1─* inquiries *─0..1 vehicles (того же клиента)
                inquiries *─0..1 services (запрошенная услуга)
customers 1─* work_orders *─1 vehicles (того же клиента)
                work_orders *─0..1 inquiries (исходное обращение)
                work_orders 1─* order_items *─0..1 services
appointments → inquiry и/или work_order (хотя бы одно)
tasks        → inquiry и/или work_order (или общая задача офиса)
activity_events → entity_type + entity_id (без FK, журнал не удаляется)
```

| Таблица | Обязательно | Может быть NULL (неизвестно) |
| --- | --- | --- |
| `customers` | имя | телефон, email, заметка |
| `vehicles` | клиент, марка | модель, год, пробег, VIN, госномер |
| `services` | код, название, категория, валюта | цена (уточняется), длительность, описание |
| `inquiries` | клиент, источник, описание, статус, дата получения | автомобиль, услуга, внешний ID, ответственный |
| `work_orders` | номер, клиент, автомобиль, статус, согласование | обращение, плановые даты, мастер, заметка, фактическое время, итоговая стоимость, дата выдачи |
| `order_items` | заказ, тип, название, цена, количество, сумма | ссылка на услугу |
| `appointments` | начало, конец, статус, источник | основание подтверждения (обязательно для подтверждённых), внешний ID |
| `tasks` | название, статус | срок, ответственный, обращение, заказ |

Правила:

- ID — UUID. Импортированные и учебные записи получают стабильные UUID, поэтому повторный импорт находит ту же запись
- Время — ISO 8601 в UTC; панель показывает его в часовом поясе бизнеса (`Europe/Moscow` по умолчанию)
- Деньги — целые копейки (`*_kopecks`) и код валюты. Количество — тысячные доли (`quantity_milli`): 4,5 л = 4500. Сумма позиции проверяется ограничением `amount = round(price × qty)`
- Позиция заказа хранит снимок названия и цены. Изменение прайса не пересчитывает старые заказы
- Удаление связанных записей запрещено (`ON DELETE RESTRICT`). Обращения, заказы, записи и задачи отменяются статусом
- `is_demo = 1` у всех учебных записей. Внешний ID уникален в паре с источником
- Каждая операция пишет событие в `activity_events` в той же транзакции. Изменяемые записи имеют `revision`; параметр `--revision N` защищает от устаревшей правки

## Статусы

Полный список с подписями: `npm run office -- statuses`.

| Сущность | Переходы |
| --- | --- |
| Обращение | `new` → `in_progress`, `waiting_customer`, `closed`; `in_progress` ↔ `waiting_customer`; `closed` → `in_progress`; `converted` ставится только при создании заказа |
| Заказ | `draft` → `awaiting_approval` → `approved` → `in_progress` → `ready` → `completed`; отмена возможна до статуса `ready`; из `awaiting_approval` и `ready` можно вернуться на шаг назад |
| Стоимость | `not_requested` → `requested` → `approved` или `declined`; одобрение фиксирует сумму, время и основание |
| Запись | `tentative` → `confirmed` → `arrived` → `completed`; `no_show`, `cancelled` |
| Задача | `open`, `in_progress`, `done`, `cancelled`; закрытую можно открыть снова |

Ограничения в базе: заказ не может быть согласован или выполнен без согласованной стоимости; запись не может быть подтверждена без основания; позиции меняются только в черновике заказа.

## Факты выполненных работ

Миграция `002_work_results.sql` готовит базу к регистрации отчётов о выполненных работах:

| Поле `work_orders` | Смысл | Правила |
| --- | --- | --- |
| `actual_duration_minutes` | реальное время работ по заказу | 1–525600 минут; только в статусах `ready` и `completed` |
| `final_total_kopecks` | итоговая стоимость ремонта | ≥ 0; только в `ready` и `completed`; не зависит от позиций |
| `completed_at` | фактическая выдача (была в 001) | ISO UTC с `Z`, проверяется триггером; можно задним числом, не в будущем |

- Нормативная длительность услуг (`services.duration_minutes`) и время записи (`appointments`) остаются отдельными и не пересчитываются
- `approved_total_kopecks` — сумма, согласованная до работ; `final_total_kopecks` — итог после них. Разбивка на работы и запчасти может быть неизвестна: искусственные позиции не создаются, панель показывает «стоимость записана общей суммой»
- Заказ без позиций можно отправить на согласование; при `order:cost --decision approved` для него обязательна `--total`. Для заказа с позициями сумма по-прежнему считается по позициям
- Возврат `ready → in_progress` стирает фактическое время и итог; прежние значения остаются в журнале
- Факты меняет `order:result` с обязательным `--basis`; событие `work_result_recorded` хранит прежние и новые значения

## Сопоставление автомобиля

Миграция `003_work_reports.sql` добавляет `work_orders.performed_on` — день выполнения,
отдельный от времени выдачи. Он виден в карточке заказа панели. `report:register` принимает
один структурированный JSON через UTF-8 stdin; `--dry-run` откатывает весь пробный прогон.
`show customer|vehicle|inquiry|order --id ID` возвращает JSON для проверки связей и результата.

| Поле `report:register` | Контракт |
| --- | --- |
| `vehicleId`, `identityConfirmed` | существующий проверенный автомобиль, строго `true` |
| `performedOn` | реальный день YYYY-MM-DD, не будущий в часовом поясе бизнеса |
| `works` | непустой массив названий, без цен из каталога |
| `finalTotalKopecks` | целые копейки, ≥ 0 |
| `actualDurationMinutes` | целые 1–525600 или null, без подмены нормативами |
| `durationNote`, `note` | необязательные пояснения длительности и дополнительные сведения |
| `basis` | реальный источник фактов |
| `orderId`, `revision` | существующий заказ и точная revision из `show`; без них создаётся новый |
| `inquiryId` | необязательно, открытое обращение для нового заказа того же клиента и автомобиля |
| `newOrderConfirmed` | `true` только после подтверждения отдельного ремонта при наличии активных заказов |
| `costApprovalBasis` | требуется для нового или чернового заказа: основание согласования стоимости клиентом |
| `approvedTotalKopecks` | необязательная согласованная сумма; без неё используется итог; при наличии позиций совпадает с их суммой |

Результат: `status` = `preview`, `registered` или `existing`, `order` — заказ, прочитанный из базы.

Регистрация атомарна для одного ремонта: заказ, факты, перечень работ в заметке и событие
`work_report_registered` в существующем журнале. Общая сумма не раскладывается на фиктивные
позиции. Для нового заказа нужно действительное основание согласования стоимости клиентом;
запись факта ремонта не доказывает оплату или выдачу. Новый заказ остаётся готовым к выдаче.
Повтор одинаковых структурированных фактов возвращает прежний заказ без новых событий.
Перефразированные отчёты и исправления Codex проверяет по истории: точная дедупликация
не заменяет уточнение смысла. Части сообщения по разным машинам сохраняются независимо.

`npm run office -- match [--vin ...] [--plate ...] [--phone ...]` только читает базу и возвращает кандидатов с причинами совпадения, расхождениями, числом прежних заказов, датой последнего и активными заказами.

- VIN уникален и хранится в канонической записи (17 заглавных символов без I, O, Q, проверка триггером). Принимается и хвост VIN из 5–16 символов
- `vehicles.plate_key` — госномер без пробелов и дефисов, кириллица номерного алфавита заменена латиницей. Номер не уникален
- Телефон сверяет CustomerProvider по нормализованному `+7XXXXXXXXXX` в CRM; в офисной базе телефона и его ключа нет. Телефон не уникален
- Ключ госномера — генерируемая колонка с индексом. Правило продублировано в `office/lib/domain.mjs`, тест сверяет SQL и JS
- Вывод `match` содержит `client_id` и автомобили, без контактов клиента

| `verdict` | Что делать |
| --- | --- |
| `match` + `strong` | VIN, или номер вместе с телефоном или хвостом VIN, без расхождений: можно использовать |
| `match` + `weak` | одно слабое совпадение (только номер, только телефон, хвост VIN): подтвердить у владельца |
| `customer_only` | клиент найден по телефону, машины у него нет: уточнить, новая ли это машина |
| `ambiguous` | несколько равных кандидатов или данные отчёта противоречат лучшему: уточнить |
| `none` | ничего не найдено: новый клиент или данные записаны иначе |

## Панель

`npm run office:serve` запускает сервер на `127.0.0.1:4180` (`--port` или `FRONTSMITH_OFFICE_PORT`; 4173/4174 заняты предпросмотрами). Сервер:

- отвечает только на GET/HEAD, остальные методы получают 405;
- принимает запросы только с Host `127.0.0.1` или `localhost`;
- отдаёт JSON и файлы из `office/public/`; SQL, путь к базе и приватные файлы недоступны;
- открывает базу только для чтения.

Разделы: обзор, клиенты и автомобили, обращения и заказы, выполненные работы, задачи, услуги и цены, расписание. Обновление — polling раз в 20 секунд и кнопка «Обновить». При ошибке панель помечает последние данные устаревшими и не показывает нули вместо отсутствующих данных. «Стоимость активных заказов» учитывает по каждому заказу итоговую стоимость, при её отсутствии — согласованную сумму, затем оценку по позициям. Оплаты не учитываются.

«Выполненные работы» (`#/results`) показывает до 200 ремонтов с `performed_on` в статусах «Готов к выдаче» и «Выдан», сначала последние по дню выполнения. Доступны поиск по работе, клиенту, автомобилю и госномеру, включительные границы периода и фильтр выдачи. API: `/api/orders?performed=yes&from=2026-10-01&to=2026-10-31`. Карточка заказа показывает структурированный перечень работ, основание отчёта и пояснение длительности из события `work_report_registered`. Дни не переводятся в часы; день выполнения не означает выдачу автомобиля. Последние восемь ремонтов доступны также в обзоре.

В начале обзора расположен месячный дашборд: стоимость выполненных работ, количество ремонтов и график по календарным дням. Столбцы используют левую денежную шкалу, линия — правую шкалу количества. Кнопки со стрелками переключают месяцы; по умолчанию выбран текущий месяц в часовом поясе бизнеса. `/api/overview?month=2026-10` возвращает агрегат `monthlyWork` по всем заказам с `performed_on` в статусах «Готов к выдаче» и «Выдан», без лимита списка. Сумма берётся только из `final_total_kopecks`; неизвестные суммы отмечаются отдельно, разные валюты не складываются. Под графиком можно раскрыть таблицу по дням и перейти к ремонтам выбранного дня. Оплаты не учитываются.

API: `/api/health`, `/api/meta`, `/api/overview`, `/api/customers[/:id]`, `/api/vehicles/:id`, `/api/inquiries[/:id]`, `/api/orders[/:id]`, `/api/tasks`, `/api/services`, `/api/schedule`, `/api/events`.

## Резервная копия и восстановление

```bash
npm run office:backup                                   # <data-root>/backups/office/office-<время>.sqlite
npm run office:backup -- --to D:/backups/office.sqlite  # путь вне репозитория
npm run office:restore -- --from <файл копии> --confirm
npm run backups:relocate                                # план переноса прежних копий из .frontsmith/business/backups/
```

- Копия делается через SQLite backup API драйвера: она включает изменения из WAL и не требует остановки CLI
- Каждая копия проверяется `integrity_check` и `foreign_key_check`
- Перед восстановлением текущая база сохраняется в `<data-root>/backups/office/office-before-restore-*.sqlite`
- Перед восстановлением остановите панель: на Windows открытый файл нельзя заменить
- Не копируйте `office.sqlite` вручную во время работы: без `-wal` копия может быть неполной
- Копия может содержать персональные данные (контакты до схемы 004, свободные тексты), поэтому по умолчанию лежит в каталоге данных Frontsmith с доступом только текущему пользователю; `--to` внутрь репозитория отклоняется. Для защиты от потери диска копируйте файлы копий на другой носитель
- `npm run backups:relocate -- --confirm` копирует прежние копии из рабочей области в `<data-root>/backups/workspace-legacy/` байт в байт вместе с `-wal`/`-shm`, сверяет SHA-256 и пишет манифест без содержимого; исходники не удаляет

## Проверки

`npm run test:office` проверяет миграции (включая перенос базы версии 001 и CRLF-копии файлов), повторный init/import/seed, факты работ, сопоставление автомобиля, FK и CHECK, деньги, переходы, атомарность журнала, переживание перезапуска, фильтры API, отсутствие записи через панель, копию с WAL и восстановление. Дополнительно `tests/work-reports.mjs` проверяет регистрацию разобранных отчётов, независимые машины, дни без пересчёта в часы, защиту существующих фактов, повторы, полный откат предпросмотра/ошибки и UTF-8 stdin CLI. Диалоговые сценарии для проверки самого навыка перечислены в его справочнике.
